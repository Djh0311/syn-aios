# 决策：编排与治理两轴路由 v1

日期：2026-07-13

状态：用户已拍板；产品路由原则正本，不代表自动识别与切换已经实现。

## 一句话

**是否启用主管编排，看协调复杂度；治理做到多重，看动作后果风险。两根轴独立判断。**

默认让一个能胜任的 agent 直接完成；只有任务确实需要拆分、并行、依赖协调、持续追问、独立复核或长时接力时，才升级为主管编排。治理始终保留最小底座，风险越高越严格，但低风险任务不应感受到额外流程噪音。

## 1. 为什么要分成两根轴

模型能力和上下文变强，会减少“一个 agent 装不下”的情况，但不会自动解决授权、责任、审计和可召回问题。反过来，一个动作风险很高，也不代表它一定需要多个 agent。

- **协调复杂度**回答：这件事是否需要一个主管组织多个工作单元？
- **后果风险**回答：Syn 应该用多强的授权、隔离、审计、验收和回滚保护？

不得再用“只读/写入”同时替代这两个判断，也不得用模型强弱直接推导是否需要治理。

## 2. 编排轴：什么时候升级主管

### 默认路径

一个角色能在合理上下文内完成，且没有独立复核、并行或持续协调需要时，走单 agent 直接执行。这里的“直接”仍经过 Syn 的项目身份、方案/任务包中转、权限边界、状态与审计，不等于让模型脱离工作台裸跑。

### 升级信号

满足以下一项或多项，才考虑主管编排：

1. 有两个以上真正可独立交付的工作单元；
2. 存在必须显式管理的先后依赖或合流验收；
3. 并行能够显著缩短等待时间，且文件或资源地盘可隔离；
4. 单个上下文装不下，或任务需要跨较长时间持续接力；
5. worker 可能卡住，需要主管追问、补资料、改派或收口；
6. 需要不同模型、工具、权限或独立复核来降低单点盲区。

不得为了证明多智能体而人为增加 worker。若多个工作项会争用同一批文件或共享状态，应串行或先切清边界，不能只按人数并行。

## 3. 治理轴：风险越高，护栏越强

治理的最小底座始终存在：当前项目身份、可读写范围、角色与任务包来源、运行账本、结果出处和可召回性。用户是否需要显式介入，按后果风险缩放。

| 协调复杂度 | 后果风险低 | 后果风险高 |
|---|---|---|
| 低 | 单 agent；薄护栏、留痕，用户尽量无感 | 单 agent；严格授权、沙箱、验收与回滚，不为安全硬加多 agent |
| 高 | 主管编排；可轻授权，但保留范围、成本与审计 | 完整主管编排；隔离写入、人闸、审计、合流验收与回滚 |

只读不自动等于低风险。读取凭据、客户数据、跨项目敏感材料，或可能把内容带出授权范围时，仍需严格治理。可回滚的测试项目写入也可能比敏感生产数据读取风险更低。

## 4. 站 3b 的准确解释

站 3b 状态保持 `PASS__SINGLE_WORKER__ZERO_WRITE__NOT_COMMITTED`。它有效证明了真实项目上的单 worker、只读、零写入控制通路和审计闭环；它没有证明：

- 多 worker 拆分与并行有效；
- `follow_up` 真实追问闭环有效；
- 主管编排比单 agent 更有产出价值；
- 写任务、其它真实项目或自动连环已获授权。

因此，3b 是**低风险真实控制通路验收**，不是**多智能体编排价值验收**。无需否定或重做 3b，也不再用同类轻量只读单继续证明主管价值。

## 5. 后续验证主管价值的最低条件

未来若重新验证主管编排，应选择可隔离、可回滚，而且确实具备上述升级信号的任务。至少应覆盖：

- 两个以上真实可分工作项，而不是人为拆人头；
- 一条明确依赖或一次真实卡住后的 follow-up；
- 每个 worker 清楚的读写地盘，必要时使用隔离工作树；
- Syn 统一收报告、核证据、合流验收；
- 越界停止、重复派发防护和可恢复基线。

具体测试项目与时间另行拍板；本文不启动新发射、不扩大授权。
