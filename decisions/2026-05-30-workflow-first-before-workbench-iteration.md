# 决策：先做真实工作流闭环，再迭代工作台

## 结论

当前仍优先做工作流。

“项目团队工作区 v1”的方向保留，但不抢当前阶段优先级。它应作为工作流闭环跑通后的工作台表达层，而不是当前先做的主任务。

## 大白话

先把工作流做成真的。

真的意思是：

- 总指导能产生明确工作项。
- 工作项能绑定到 Codex 会话。
- 工作台能向绑定会话派发指令。
- 能等待执行结束。
- 能读回结果。
- 能写派发记录和审计。
- 总指导能根据结果决定下一步。

只有这条链路成立，后面才可能用工作流快速迭代工作台本身。

## 依据

- 用户明确表示：认可“项目团队工作区 v1”的表达，但仍然想先做工作流。
- `CURRENT.md` 当前主线已经是 Codex 会话管理 + Codex 工作流编排。
- `archive/handoffs/2026-05-29-desktop-shell-workflow-node-dispatch-codex-instruction-v1-review.md` 已接受派发代码路径，但明确真实业务自动工作流尚未完成。
- `evidence/2026-05-29-reference-workflow-session-node-research-v1.md` 说明会话可以作为可见工作单元，但底层仍需要工作流状态账本。

## 对当前顺序的影响

当前先做：

1. 工作流节点 safe probe 真实确认派发。
2. 派发结果读回和总指导回收判断。
3. 长任务、权限确认、失败重试、超时取消的最小协议。
4. 用这套闭环执行一个很小的真实工作台迭代任务。

之后再做：

- 项目团队工作区 v1。
- 会话按角色摆放。
- 工作项、证据、交接、审核、权限队列同屏。

## 不做

- 不先做纯 UI 工作区来替代真实工作流。
- 不把会话列表包装成工作流完成。
- 不把 safe probe 说成真实业务自动编排。
- 不把任务包重新放回主界面中心。

## 风险

- 如果先做团队工作区 UI，容易变成看起来像协作，实际不能自动推进。
- 如果只做底层工作流而完全不考虑工作区表达，后续用户仍然看不懂系统在做什么。
- 所以折中是：当前先打通运行闭环，同时保留“会话作为可见工作单元”的展示规则。
