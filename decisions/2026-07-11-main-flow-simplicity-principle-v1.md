# 决策:主流程简单性原则(规则为流程服务)v1

日期:2026-07-11 · 拍板人:用户(原话:「底层的规则太死板了,我想要的是:我给 LM 说需求,LM 返回之后我看过方案、觉得没问题、工作流也没问题、允许开始,就可以开干了——非常简单的需求」)。

## 原则(北极星表述)

**说需求 → 看方案+工序图 → [允许并开始] → 开干。** 这条主流程必须丝滑:
1. **人闸保留且唯一**:「我看过、我允许」那一下不省(用户原话自带);人闸**之外**不许再有用户可感知的机器卡顿;
2. **规则为流程服务,不许流程迁就规则**:状态机/锁/中间态是实现手段——它们卡住主流程 = 实现的 bug,不是用户操作的错;
3. **失败自愈优先于失败呈现**:瞬时故障(锁竞态/复核迟到/快照旧)应自动重试/自动补齐,机器能自己走的路不许停下来等人;必须停时才呈现(永不冻·死配对按钮);
4. **中间态最少化**:每个用户可感知的中间状态都要有存在理由;审计它们的第一问是「能不能删」,不是「怎么给它补个按钮」。

## 背景(为什么现在拍)

07-10~11 真机连撞同族问题:锁竞态一撞就停、合流失败留死脸、授权悬在 pending 无人认领——每个都是「规则死板卡住简单需求」的实例。逐个补丁治标;本原则 + 失败路径系统审计(`tasks/2026-07-11-state-machine-failure-path-audit-v1.md`)治本。

## 边界

- 不砍人闸/path-lock/审计落账(AGENTS 高危清单照旧)——简单性是给**主流程体验**的,不是给安全边界的;
- 「自动连环/多项目」仍 Phase E 重档——本原则管单条链内的丝滑,不扩自动化范围。
