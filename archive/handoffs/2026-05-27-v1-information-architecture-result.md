# 第一版信息架构交接

## 回收对象

- 任务包：`product-line/tasks/2026-05-27-v1-information-architecture.md`
- 开发线：信息架构线
- 回传 evidence：`product-line/evidence/2026-05-27-v1-information-architecture.md`

## 结论

建议接受为第一版桌面应用页面结构 handoff。

这个 handoff 只定义第一版页面、字段来源、未知点和阶段边界；不定义 UI 框架，不写应用代码，不设计自动写入 Codex 状态库的交互。

依据：

- 任务包要求输出页面结构 handoff。
- `product-line/README.md` 定义第一版为只读治理 Codex。
- `product-line/STAGE_PLAN.md` 把桌面应用壳放在阶段 2，把任务线登记放在阶段 3，把可控写入放在阶段 4。

## 先说薄弱点

- 第一版如果只做“列表”，会变成另一个文件浏览器。需要在项目页把会话、skills、harness、handoff / evidence 合到同一个项目上下文里。依据：用户的混乱来自项目、对话、skills、harness 关系乱。
- harness 页面第一版只能显示候选入口、运行记录字段和人工判断位，不能自动判断“有用”或“没用”。依据：当前没有可验证的因果数据，且第一版是只读治理。
- skills 适配不能自动给强结论。依据：当前只知道 skills 来源多样，没有项目适用规则和历史效果数据。
- 对话迁移、删除、撤销虽然可参考 Codex++，但第一版不能做。依据：第一版禁止写 Codex 状态库；迁移删除会触碰 Codex 内部状态。
- 移动端统一管理界面属于最终蓝图，不属于第一版。依据：阶段计划阶段 2 只有桌面应用壳，没有移动端目标。

## 第一版页面

第一版固定 6 个页面：

- 首页
- 项目页
- 会话页
- skills 页
- harness 页
- 任务线页

依据：任务包目标明确要求这些页面展示哪些字段。

## 总体信息结构

核心对象关系：

```text
项目
  关联会话
  关联 skills
  关联 harness
  关联 handoff / evidence / README / AGENTS
  关联任务线
```

第一版入口顺序：

```text
首页 -> 项目页 -> 会话页
首页 -> skills 页
首页 -> harness 页
首页 -> 任务线页
```

设计判断：

- 项目优先，Codex 是第一版唯一 agent。依据：用户主要痛点是 ERP 和游戏项目差异大；README 也明确第一版先做 Codex。
- 页面只读展示，低风险操作仅限打开文件夹、复制路径、定位日志。依据：STAGE_PLAN 阶段 2。

## 首页

用途：

- 作为 Codex 治理总览，不做复杂编辑。
- 快速看到最近项目、异常、待处理任务线。

展示字段：

- 当前接入对象：Codex。
- 项目数量、活跃项目数量、最近活跃项目。
- 最近会话数量、归档会话数量、无项目或归属异常会话数量。
- skills 数量、本地 skills 数量、插件内 skills 数量。
- harness 候选数量、缺少验证入口的项目数量。
- 任务线状态摘要：待派发、进行中、已回收、暂停。
- 数据更新时间、索引 warning 数量。

字段来源：

- 项目、会话、skills、warning：阶段 1 只读索引 JSON。
- 任务线状态：`product-line/tasks/README.md` 和 `product-line/tasks/*.md`。
- 当前接入对象和第一版范围：`product-line/README.md`。

未知点：

- 索引 JSON 最终是否直接提供所有统计字段，还是由 UI 层聚合。
- “活跃项目”阈值按最近更新时间算，还是按未归档会话算。
- 无项目会话是否由索引内核直接标记。

第一版不做：

- 不显示 OpenClaw、VS Code、Claude Code 主入口。
- 不做移动端入口。
- 不在首页执行对话迁移、删除、归档。

阶段 2 可实现：

- 只读总览。
- 点击进入项目、会话、skills、harness、任务线。
- 打开项目文件夹、复制路径、定位日志。

## 项目页

用途：

- 第一版核心页面。
- 把一个项目下的会话、skills、harness、handoff / evidence 和风险放在一起。

通用展示字段：

- 项目名称或路径尾名。
- 项目根路径。
- 项目类型：ERP、游戏、未知。
- 最近活跃时间。
- 会话数、活跃会话数、归档会话数。
- 当前权威入口：README、AGENTS、handoff、evidence、阶段计划或项目文档候选。
- 关联 skills 候选。
- 关联 harness 候选。
- 常用验证命令候选。
- 风险提示：缺少 README、缺少 AGENTS、没有 handoff / evidence、归属异常、索引 warning。

字段来源：

- 项目根路径、会话数、最近活跃时间：阶段 1 只读索引 JSON。
- README、AGENTS、handoff、evidence 候选：项目文件扫描结果。
- 项目类型：项目显式配置、任务文档、路径或人工标注；没有依据时显示未知。
- skills / harness 候选：索引内核扫描结果和项目文件扫描结果。

ERP 项目额外字段：

- 后端、管理端、移动端或骑手端等子系统候选。
- 数据库迁移、接口服务、前端构建、端到端检查等验证命令候选。
- 权限、数据迁移、接口联调、环境变量敏感项风险提示。

ERP 字段依据：

- 用户明确说存在大型 ERP 系统。
- ERP 常见风险涉及数据库、权限和多端联调；但具体子系统名称必须来自项目文件或人工标注，不能由 UI 猜。

游戏项目额外字段：

- 游戏引擎或运行方式候选。
- 资源目录、构建目录、截图或试玩验证入口候选。
- 玩法测试、画面渲染、资源导入、性能风险提示。

游戏字段依据：

- 用户明确说存在游戏开发项目。
- 具体引擎、资源管线和测试方式必须从项目文件或人工标注来，不能由 UI 猜。

未知点：

- 项目类型是否已有权威配置文件。
- harness 命令是否能从 package、Makefile、脚本目录或文档稳定提取。
- “当前权威入口”是否由总指导文件维护，还是由索引按文件名候选推断。

第一版不做：

- 不自动修改项目配置。
- 不自动安装或启用 skills。
- 不自动运行 harness。
- 不自动判定项目类型，除非已有明确配置或文档依据。

阶段 2 可实现：

- 项目详情只读展示。
- 打开项目文件夹、复制项目路径。
- 定位 README、AGENTS、handoff、evidence 文件。

阶段 3 才实现：

- 登记 current / paused / historical / superseded。
- 在工作台里生成任务包、回收结果摘要。

阶段 4 才实现：

- 在严格确认下写项目级配置。

## 会话页

用途：

- 展示 Codex 会话和项目的关系。
- 帮用户知道每个会话在做什么、属于哪个项目、风险在哪里。

展示字段：

- 会话标题。
- 会话编号。
- 所属项目路径。
- 创建时间、更新时间。
- 是否归档。
- 来源：用户会话、子任务、未知。
- 模型和推理配置摘要。
- token 使用摘要。
- rollout 日志路径。
- rollout 是否存在。
- 会话 warning。
- 关联 handoff / evidence 候选。

字段来源：

- 会话元数据：阶段 1 只读索引 JSON。
- rollout 路径存在性：阶段 1 只读索引 JSON。
- 所属项目：Codex SQLite 中的 `threads.cwd` 经索引内核输出；`.codex-global-state.json` 只能作为 UI 提示来源。
- handoff / evidence 候选：项目文件扫描结果。

未知点：

- 会话标题可能包含过多上下文，UI 是否需要继续截断。
- 会话正文第一版是否完全不读，还是只读摘要；当前建议不读正文。
- 子任务来源字段是否能稳定解析。

第一版不做：

- 不嵌入 Codex 聊天窗口。
- 不展示完整会话正文。
- 不迁移会话归属。
- 不删除、归档或恢复会话。
- 不写 Codex 状态库。

阶段 2 可实现：

- 只读会话列表和详情。
- 复制会话编号、复制 rollout 路径、定位日志文件。

后续阶段再评估：

- 对话迁移、删除、备份、撤销。
- 这些能力必须有备份、预览、失败状态和恢复流程。

## skills 页

用途：

- 管理 Codex skills 的只读台账。
- 让用户知道 skill 来自哪里、可能适合哪些项目、是否缺少元数据。

展示字段：

- skill 名称。
- 来源：本地非插件、插件内、未知。
- 所在路径。
- 所属插件名称或目录。
- 描述或 manifest 摘要候选。
- 适用项目候选。
- 最近修改时间。
- 状态：可见、缺少说明、解析失败、未知。
- 风险：来源不明、manifest 损坏、编码异常、重复名称。

字段来源：

- skills 目录和插件 cache：阶段 1 只读索引 JSON。
- manifest 摘要：索引内核扫描结果。
- 适用项目候选：项目标注、任务文档或人工维护；无依据时显示未知。

未知点：

- 不同来源 skill 的 manifest 字段是否统一。
- skill 版本号是否可靠存在。
- skill 和项目的适配关系是否已有人工标注。

第一版不做：

- 不自动安装 skill。
- 不自动删除 skill。
- 不自动启用或禁用 skill。
- 不把“适用项目候选”说成确定适用。

阶段 2 可实现：

- 只读列表、筛选来源、按项目查看候选。
- 打开 skill 路径、复制路径。

后续阶段再评估：

- skills 仓库。
- 项目级 skills 推荐。
- 自动索引仓库或安装。

## harness 页

用途：

- 记录每个项目的验证入口和运行作用线索。
- 第一版先做候选台账，不做自动因果判断。

展示字段：

- harness 名称或命令名。
- 所属项目。
- 类型：测试、构建、启动、迁移、截图、试玩、发布前检查、未知。
- 命令或入口路径。
- 说明来源：package、Makefile、脚本、README、AGENTS、handoff、人工标注、未知。
- 最近运行记录候选。
- 最近结果候选：通过、失败、未知。
- 覆盖范围候选：后端、前端、数据库、移动端、游戏玩法、资源、未知。
- 作用判断状态：未评估、人工确认有用、人工确认废弃、需要加强。
- 证据链接：日志、handoff、evidence、测试报告候选。

字段来源：

- harness 候选：索引内核和项目文件扫描结果。
- 运行记录：后续验证线或项目内日志；第一版如果没有记录就显示未知。
- 作用判断：人工标注或后续阶段的评估结果；第一版不自动生成。

ERP 项目重点：

- 数据库迁移检查。
- API 服务启动和健康检查。
- 管理端、移动端、骑手端等前端构建或运行检查。
- 权限、数据一致性、接口联调检查。

游戏项目重点：

- 游戏运行入口。
- 构建命令。
- 截图或浏览器试玩检查。
- 资源导入、性能、画面渲染检查。

未知点：

- harness 是否已有统一命名。
- 运行日志是否可稳定读取。
- “有用”和“没用”的判定标准尚未定义。

第一版不做：

- 不自动运行 harness。
- 不自动废弃 harness。
- 不自动加强 harness。
- 不根据单次通过或失败判断 harness 价值。

阶段 2 可实现：

- 候选 harness 台账。
- 按项目和类型筛选。
- 复制命令、打开入口文件。

阶段 3 / 4 后再实现：

- 人工登记作用判断。
- 写项目级验证命令清单。
- 基于多次运行记录做辅助评估。

## 给 UI 实现线的建议

- 页面先按项目组织，不要先按 agent 组织。依据：第一版只有 Codex，且用户的真实差异来自 ERP 和游戏项目。
- 所有不确定字段都要显示“未知”或“缺少依据”，不要空白吞掉。依据：用户要求不要假装理解，结论要有依据。
- 会话标题默认截断，详情页也不要直接展示完整正文。依据：会话标题和正文可能携带过多上下文。
- `.codex-global-state.json` 只能当 UI 提示来源，不要覆盖项目归属。依据：已有产品线结论把 `threads.cwd` 作为项目归属权威来源。
- harness 页面要保留人工判断位，但第一版只读，不写回。依据：用户有 harness 治理需求，阶段边界不允许第一版写配置。
