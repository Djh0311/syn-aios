## 方法说明

范围 = 前端根 `prototypes/productized-desktop-shell/src/` 全部界面文件（导航正本 `lib/workbenchNavigation.ts` 定义的全部视图 + 项目页内部全部子面 + 右栏六项 + 跨面共享组件），共约 25000 行代码、90+ 个文件，拆成 **11 个集群**并行体检，每个集群独立完整读完分配文件，逐条对照正本产出体检行（含代码证据）。总指导收到 11 份结构化结果后，做了两件事：

1. **抽样核实**：对全部 13 条 P0 发现里的关键代码引用做了独立 grep/Read 复核（详见各条证据行号），5 处抽样全部命中，未发现捏造或引用错误。
2. **交叉去重与仲裁**：多个集群独立触达同一个 friction-log 条目或同一处代码时，如实保留了各自的独立核实结论（包括互相印证、互相补充、甚至一处排除嫌疑的情况），未做强行合并——详见 §三。

体检行颗粒度 = "面"（能被唯一问题定义的界面单元），不是文件；一个大文件常拆成好几行，几个小文件也可能合并成一行。严重度判据：**P0=挡用户**（唯一问题答不出来/操作入口缺失或无效）、**P1=违宪**（明确违反正本某条但用户仍能勉强完成任务）、**P2=打磨**（视觉/文案/一致性瑕疵，不违反硬条款）。档位判据（深磨/够用/待定）：数据形态仍在后端演进区（M5-B/L2/站4等）的面倾向"够用"；纯呈现/结构问题不依赖后端形状变化的倾向"深磨"；总指导判断不了归因的如实标"待定"，留给用户/总指导裁决。

### 七个最该先看的发现（P0 级/红线级，已逐条代码核实）

1. **发令台构成宪法明令禁止的"第二入口"**——一句自由文本（"按计划跑 X"）直接触发真实工作流执行，完全跳过项目>工作流>工单的对象层级和批态"写根/工具/边界"可见性承诺。（`WorkflowCommandConsoleView.tsx:97-148`）
2. **"没有能允许的选项"（friction #4）已定位到两个独立断点**，都与站4后端进度无关：① `ProjectJiaobanPanel.tsx:2332` 的写单授权提示只有一段文字和一个不可交互图标，没有任何按钮；② 智能体页"H2 真实恢复授权"面自称"只读材料"，结构性缺批准按钮。PermissionDialog.tsx 本身经逐一核查~30余种场景按钮完整，**已排除嫌疑**。
3. **"重新看一遍"点了没用（friction #3）已确诊为真实前端 bug**，根因精确到一行：`ProjectJiaobanPanel.tsx:1503-1504` 的 loading 判断公式里 `!boundaryForThisProposal` 一项，导致方案已有旧结果时新请求的 loading 态永不上屏。
4. **记忆中心"没法看"的根因已找到**：详情面板硬编码绑定列表第一项（`summary.formal_memories[0]`），列表卡片组件不接受 onClick——不是"要点很多步"，是**除第一条外的记录永久点不开**；同时高级治理/日常候选收件箱多处硬编码 `slice(0, 3/4)` 截断且无查看全部入口。
5. **交货态"证据"在展示层被物理删除，不是折叠隐藏**：`ProjectWorkflowExecutionPanels.tsx:608-609/634` 两处注释自认"砍：阶段门禁摘要卡+未决项+后置项明细列表"——用户展开折叠也只能看到"通过/需修改/阻断"三个字，没有任何路径核实这个结论，直接对应 friction #7"噪音多、关键结论被埋没"。
6. **说态方案卡系统性地不渲染 AI 自己开出的验收标准**：`ProjectConsultationProposalCard`（治理面）和 `JiaobanAuthorizeState`（交办主面）两处独立代码都拿到了 `proposed_steps`/`acceptance_criteria` 字段但从未渲染，用户看到的方案卡永远只有一句目标复述或一大坨顿号拼接的长句（friction #2 的直接代码成因）。
7. **技能库 90 条技能里超过 6 条的部分，在产品任何路径下都不可达**（`SkillsBoardView.tsx:14 skills.slice(0,6)`，且不像运行器面有开发者详情兜底全量）——与记忆中心同款"硬编码截断无查看全部入口"的坏味道在多处重复出现，是一个跨面的系统性模式，不是孤立疏漏。

### 需要用户/总指导裁决的开放问题（AI 判断不了归属，如实标注，不强行下结论）

- **"想法箱"占一等主导航却零真实功能**（`view==="ideas"`→ 纯占位组件），13个P0之一但档位标"待定"——这是产品决策（保留位置等后端接线 / 现在就降级），不是前端能自主判断的事。
- **"智能体"与"项目"在主导航"主入口"分组里同权重并列**，字面贴近正本§二红线"任何态都不许把 agent 提为最高对象"，但正本§六D1 又明确承认"智能体页=回顾面合法例子"——存在解读张力，需要总指导核实正本原意。
- 若干"档位=待定"的项（HomeView 变更空态、ProjectGallery 搜索、ProjectAgentMovedPanel 等）依赖产品对某功能是否要恢复/接入的判断，本轮不强行下深磨/够用结论。

## 二、IA 审计（对象层级 / 导航深度 / 入口一致性，对照正本§二）

以下按三轴汇总全部 11 集群产出的 IA 专项发现（体检行里同时也有对应行，此处是横切汇总，方便一次性看清结构性问题）：
- **[入口一致性][P1]**（IA_NAV）workbenchNavigation.ts 里同时存在三份口径不一致的"主导航是什么"：primaryNavItems(扁平8项，不含command-console)、primaryNavGroups(4组11项，含command-console，WorkbenchShell.tsx实际渲染用)、navItems(=homeNavItem+primaryNavItems+settingsNavItem共10项，全仓零处被外部导入，纯死代码)。primaryNavItems目前只在App.tsx里用于stageKInitialViewKeys白名单校验，而它缺失command-console，导致一个可复现的功能性缺口：VITE_STAGE_K_INITIAL_VIEW=command-console时会静默回退到home，尽管command-console是primaryNavGroups"flow"组里UI上一键可达的一等主入口。
  证据：lib/workbenchNavigation.ts:35-44(primaryNavItems，8项，无command-console) 对照 :46-80(primaryNavGroups，"flow"组:55-63含 { key: "command-console", label: "发令台" } 在:61) 对照 :90-94(navItems定义，grep全仓"navItems\\b"仅命中该定义行本身，零外部import) ； App.tsx:87-92 `const stageKInitialViewKeys = new Set<ViewKey>([homeNavItem.key, ...primaryNavItems.map(item=>item.key), settingsNavItem.key, ...devNavItems.map(item=>item.key)]);` 和 :94-98 `stageKInitialView()` 白名单校验逻辑，未使用primaryNavGroups；WorkbenchShell.tsx:14 单独import了primaryNavItems但grep确认该文件内除import行外零处使用（真实渲染用的是:222 primaryNavGroups.map）。
- **[对象层级][P1]**（IA_NAV）primaryNavGroups的"main"（主入口）分组把"智能体"(agents)与"项目"(projects)并列放在同一顶层导航分组、同等视觉权重，字面上贴近宪法§二红线"项目永远是最高导航层与入口；任何态都不许把agent/chat/timeline提为最高对象"。但需要注意：宪法§六D1同时明确把"智能体页"列为"回顾面"（跨单检索面）的合法例子之一，说明智能体页本身作为回顾面存在并不违宪；本条真正的问题是当前UI在结构/视觉层面完全没有区分"项目"（五态工作流主线的最高对象）与"智能体"（回顾面/跨会话检索入口）——两者被塞进同一个不加区分的"主入口"分组里，容易让用户和后续开发者误读为二者是平级的最高导航对象。这是需要总指导核实§二与§六D1如何协调解读的边界问题，不宜简单判定为"完全违宪"或"完全合规"。
  证据：lib/workbenchNavigation.ts:47-54 `{ key: "main", label: "主入口", items: [{ key: "projects", label: "项目" }, { key: "agents", label: "智能体" }] }`；WorkbenchShell.tsx:222-240 `primaryNavGroups.map(...)` 原样渲染，group内部用同一个.nav-list容器、同一个.nav-item按钮样式渲染每一项，projects和agents在DOM结构和CSS类名上完全等价，没有任何标记区分"五态主线对象"与"回顾面入口"。

  证据：lib/workbenchNavigation.ts:33 `export const homeNavItem: WorkbenchNavItem = { key: "home", label: "首页", glyph: "⌂" };` 对照 WorkbenchShell.tsx:174-176 `<button className="topbar-seal-button" ... aria-label="回到首页" title="首页"><span className="brand-mark">案</span></button>`（未import homeNavItem，也未使用其.glyph/.label）；对照WorkbenchShell.tsx:242-251 settingsNavItem的正确用法 `<span className="nav-glyph">{settingsNavItem.glyph}</span><span className="nav-label">{settingsNavItem.label}</span>`。
