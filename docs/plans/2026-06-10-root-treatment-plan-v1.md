## 0. 这份方案治什么

一句话：**现有制度管住了"谁能做什么"（行为），没管住"代码长成什么样"（形状）。本方案给制度补上"形状"这一半，再用补好的制度分批还旧债。**

先确认保留的部分：方案授权制、任务包、evidence / handoff、验收口径（accepted_with_deferred_items 文化）、角色边界——这套东西已被 146 个任务包验证有效，**全部保留，不推翻**。本方案是给它补一个缺的轮子，不是换车。

## 1. 病根诊断

### 1.1 表症（2026-06-10 实测数据）

| 项 | 实测值 |
|---|---|
| `src-tauri/src/lib.rs` | 25,925 行 |
| `real_execution_command.rs` | 8,763 行 |
| `ProjectsView.tsx` | 6,069 行 |
| 离线测试主文件（单文件） | 9,369 行 |
| 生产用 sidecar JSON 种类 | 15 种，互相无事务 |
| `workflow-state.v0.json` | 全局单文件 2MB，所有项目共用 |
| `backups/` 目录 | 227 份备份，184MB，只增不清 |
| `WorkbenchSnapshot` | 18 个顶层字段整包加载，前端 `types.ts` 5,149 行 |
| tauri command 总数 | 96 个 |

佐证：J3 验收口径已自记"跨 store 原子性未完整解决"；架构文档自记"lib.rs 承担过多职责，需要拆出领域模型、应用服务、适配器、存储模块"——问题是已知的，但没有机制认领它。

### 1.2 病根（一个）

**任务包制度在结构上奖励加法、惩罚重构。**每个任务包为守住"改动最小、不越界"（这本身是制度优点），都选择往现有文件里加代码；而"拆 lib.rs"从来不是任何任务包的验收目标，所以永远排不上队。七层架构文档写了正确的形状，但没有任何机制强制代码服从它——结果代码按任务包历史生长，不按架构生长。

### 1.3 为什么必须治

worker 是 agent。巨石文件超出 agent 能稳定持有的上下文 → worker 出错率升高 → 审查和返工增多 → 用户确认负担加重。**形状问题对人类团队是慢性病，对 agent 团队是战斗力问题。**后续多 agent 并行（H-I 路线的终点）会把"无事务、无锁"从理论风险变成真实事故。

## 2. 治疗原则

1. **先换生长机制，再搬家。**先立规矩（R0），让新代码停止长歪；再分批还旧债（R2-R4）。顺序不能反，否则边搬边长。
2. **"agent 能稳定干活"就是本项目的可维护性。**一切形状指标以"单个 worker 能在上下文里装下它要改的模块"为准绳。
3. **冻结集中治理（用户 2026-06-10 拍板）。**治理期内不开新功能任务包，产能全部投入 R0-R5；紧急缺陷修复除外（修复同样受 shape gate 约束）。复用现有 C1-C6 闭环；"行为不变"由现有测试矩阵（typecheck / offline-interaction / build / cargo test）兜底。
4. **每一步可验收、可回滚。**沿用 evidence / handoff；治理任务包额外记录形状指标前后值。

## 3. R0：制度升级（开发模式改什么）

### R0-1 形状守门（shape gate）

扩展现有 `scripts/harness/stage-k-architecture-gate.js`（或新建独立 gate 脚本），规则：

- **lib.rs 水位线，只降不升**：记录当前行数为水位线；任何任务包收口后 lib.rs 行数不得高于水位线；水位线只能下调。
- **新增 `#[tauri::command]` 不得写进 lib.rs**，必须落在 `commands/` 或对应领域模块。
- **禁止新增 sidecar 文件种类**：新的持久化需求必须进统一存储层（R3 前确需新增的，必须用户确认 + decisions/ 记录）。
- **新建文件行数上限**（建议值：Rust 3,000 / TS·TSX 2,000）；存量超限文件进"棘轮清单"，只降不升。
- **豁免必须留痕**：gate 豁免需要一条 decisions/ 记录，不允许沉默豁免。

### R0-2 任务包模板补"形状影响"必填节

每个任务包声明：新增代码落在哪个模块、是否触碰棘轮清单文件、预计行数变化。和现有"UI 显示边界确认"固定章节同级。

### R0-3 新增任务包类型：治理任务包

- 验收口径 = **行为不变（测试矩阵全绿）+ 形状指标改善（写进 evidence）**。
- 治理冻结期内，治理任务包就是默认任务包。解冻恢复功能开发后，按"每 3 个功能任务包至少 1 个治理任务包"维持形状不回潮。
- 走同一套 C1-C6 闭环，不另起炉灶。

**R0 验收**：gate 脚本上线并强制执行；模板更新；第一个治理任务包按新模板走完一轮。

## 4. R1：立即止血（小活，可与 R0 并行）

- **workflow-state 写入锁**：`workflow_state_store.rs` 当前只有原子替换（temp + rename）+ 备份，没有 session_continuation_store 那样的 StoreLock。任务包先核实上层是否有进程内互斥，再补文件级锁（实现直接照抄 session-continuation 的 StoreLock）。
- **备份保留策略**：`backups/` 加清理（建议：保留最近 30 份 + 每日 1 份，其余归档或删除；184MB 预计降到 20MB 以内）。

**R1 验收**：并发写测试通过；备份数量收敛到策略值。

---

## 5. R2：lib.rs 解体（按棘轮分批，每批一个治理任务包）

- **排序原则**：被任务包改动最频繁的领域先搬出（agent 收益最大）。
- 建议批次：
  1. 命令注册 / 分发出 lib.rs，按领域归入 `commands/` 子模块；
  2. workflow 读模型派生逻辑，与现有 `workflow_read_model.rs` 汇合；
  3. 记忆领域（与 formal_memory_store 等汇合）；
  4. 运行时 / 诊断领域；
  5. 剩余清扫。
- 阶段水位线建议：25,925 → 15,000 → 8,000 → 3,000 →（理想 <1,500，只剩应用装配）。
- 每批验收：测试矩阵全绿 + 水位线下降 + evidence 记录前后行数。

前端同理但排在 R4（与读模型拆分联动更自然）。

## 6. R3：存储统一（SQLite，治"15 个 sidecar 无事务"的根）

**设计依据已存在，本阶段是执行已批准的设计，不是新设计**：`memory-layer-design-v1.md` 第 18 节已定"SQLite 权威 + Markdown 展示 + 派生索引可重建"；`middleware-version-development-plan-v1.md` 已要求"迁移 / 双写 / 回滚方案"。

- **目标形态**：单一 `workbench.db`；15 种 sidecar 全部表化；`workflow-state.v0.json` 的 11 个顶层数组（projects / workflows / nodes / edges / work_items / artifacts / reviews / audit_events 等）天然成表；跨 store 写合并为单事务；备份改 DB 快照 + 保留策略。
- **迁移五步**（每步一个任务包）：
  1. 建 schema + 导入器（JSON→DB，幂等可重跑）；
  2. 双写期（写 DB + 写 JSON，读仍走 JSON）；
  3. 读切 DB（JSON 降级为导出格式）；
  4. 观察期收口（停写 JSON，归档）；
  5. 回滚预案演练并记录。
- **硬门槛（需用户确认）**：**R3 未收口前，不解锁多 agent 并行真实执行。**理由：并行写入会把"无事务、无锁"从理论风险变成事故。

**R3 验收**：一次"候选采纳"（跨记忆 + 审计两域）在单事务内完成；中断注入测试不产生半写状态；沿用"不能把建库建表当成记忆层完成"的原有口径。

## 7. R4：读模型与前端瘦身（排在 R3 后）

- `WorkbenchSnapshot` 拆为按页面的查询命令（项目页 / 记忆页 / 运行页 / 智能体页各自查询），不再一条命令整包加载；前端 `types.ts` 随之分域。
- `ProjectsView.tsx`（6,069 行）、`AgentView.tsx`（3,365 行）按功能区拆分。**拆分基准（2026-06-10 修订）**：按解冻后目标布局的区块切（Xuanji UI 报告 §16：四周窄栏 / 中央主界面 / 右侧详情面板 / 底部状态栏 / 悬浮入口），不按现状页面外观切——避免解冻后改布局时二次重拆。R4 不改布局本身，只决定组件边界。
- **水墨风格清单（2026-06-10 新增）**：把散在 `styles.css`（8,464 行）里的水墨古风提炼成显式风格资产（颜色表 / 字体表 / 质感规则），作为后续一切 UI 改动"只动结构、不动风格"的可验收依据（用户拍板：布局按 Xuanji 报告改，视觉风格保留水墨古风）。
- 离线测试主文件（9,369 行）按领域拆成多文件。
- 顺手项：任务包上下文注入"代码地图"（模块索引 + 各领域入口文件清单），与 M4 任务记忆包机制衔接，降低 worker 整文件阅读需求。

## 9. 最终验收口径（治疗何时算完成）

建议冻结口径（数值可调，用户拍板）：

1. lib.rs ≤ 3,000 行（理想 ≤1,500）；棘轮清单文件全部低于上限或处于下降轨道。

3. `WorkbenchSnapshot` 不再是唯一读模型；≥4 个主页面改为按页查询。
4. shape gate 在所有任务包验收中强制执行 ≥1 个完整 Stage，无沉默豁免。
5. 蓝图无 §17/§22/§26.4 矛盾；吸收文档查重完成。

最终结论按现有文化冻结（accepted / accepted_with_deferred_items 均可）。

## 10. 不接受为（边界）

本方案被确认后，也**不接受为**：

- 推翻方案授权制 / 任务包 / evidence 制度（制度保留，只补形状约束）。
- 治理冻结 = 一切活动停摆：紧急缺陷修复仍可走任务包，但同样过 shape gate，不得借修复夹带功能。
- 借机引入向量库 / 图数据库 / GraphRAG / planned adapters 真实接入（仍按原边界后置）。
- "建库建表" = 记忆层或工作流完成（沿用中间版本方案原话）。
- gate 上线 = 旧债已还（棘轮只保证不恶化，还债靠 R2-R4）。
- R3 收口前的任何多 agent 并行真实执行授权。
- 本草案未经用户确认即进入 AUTHORITY / CURRENT / 任务队列。
