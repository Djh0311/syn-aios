# B2 后下一阶段建议方案 v1

日期：2026-07-10
状态：**候选建议，尚未拍板；不改变 `CURRENT.md`，不代表 Phase C 已开工。**

> 用户已明确：此前两份前端原型**先不采纳**。本建议不继承它们的页面结构、交互、文案或实现假设；原型不作为 Phase C 的规格或验收依据。

## 0. 结论先行

建议 B2 完成端到端真机验收后，正式进入 **Phase C·智能入口**。

但 Phase C 不应被定义成“再造一个自然语言引擎”或“先做一套 Jarvis 界面”。当前项目页已经具备：

> 自由文本目标 → 项目咨询读项目并生成方案 → 方案进入 `PendingUserConfirmation` → 用户确认后复用现有执行闭环。

真正缺的，是把这条已经存在的能力**安全地接到主对话**：识别这是一个新的项目目标，绑定用户明确选中的项目与工作流，再转交现有项目咨询和 B2 闭环。

推荐的第一版一句话是：

> **在固定测试项目中，用户从主对话说一个目标；Syn 只在项目绑定明确、意图可支持时，把原话交给现有项目咨询生成待确认方案；不猜项目、不跨项目、不直接开工。用户点「允许并开始」后，才进入既有 B2 执行闭环。**

## 1. 理解、事实、未知与假设

### 1.1 已知事实

1. B2 的代码和机器闭环已经完成，但完整端到端真机验收仍待完成。证据见 `CURRENT.md` §一、§三。
2. 当前路线图下一阶段是 Phase C：主对话一句话启动，AI 形成方案，用户审后再跑；自然语言入口不能绕过方案授权。证据见 `docs/plans/2026-06-27-complete-workbench-phased-roadmap-v1.md` §3。
3. 项目是最高级业务对象，会话、工作流、权限、记忆和审计都必须围绕项目组织。证据见最终蓝图 §1–§5，以及 `docs/workbench-system-architecture-v1.md` §6。
4. 当前项目交办页已经接受自由文本目标，并调用现有 `run_project_consultation`：`prototypes/productized-desktop-shell/src/views/projects/ProjectJiaobanPanel.tsx`。
5. 现有项目咨询在生成方案后明确停止：只写入 `PendingUserConfirmation`，不自动确认、不让授权生效、不启动 worker。证据见 `prototypes/productized-desktop-shell/src-tauri/src/consultant_agent.rs`。
6. B2 已提供后半段：每任务独立会话、任务包、求助、主管终标与总结、失败四选一、审计词表和人话错误。

### 1.2 尚未确定

1. “主对话”最终落在哪个现有界面、由哪个组件承载，尚未拍板。
2. 主对话与秘书的视觉关系尚未拍板；秘书可以解释和转交，但不能因此变成派活或写状态的角色。
3. 多轮语义澄清、状态问答、停止/恢复等更多意图是否进入 Phase C 后续切片，尚未拍板。

### 1.3 本建议采用的假设

1. Phase C 首版仍只在固定测试项目运行，不解锁非测试真实项目。
2. 首版要求用户显式选中当前项目与工作流，不让模型猜项目。
3. 首版只支持一种可执行意图：**发起一个新的项目目标**。
4. 具体 UI 后置到行为契约拍定之后；现有左侧栏和现有项目入口保持不动。

## 2. 先说风险和反对意见

### 2.1 最大风险：把 Phase C 做成第二套 NL 引擎

项目页今天已经能接收一句自然语言目标并生成方案。若另建“NL 拆解器 → 新方案对象 → 新执行入口”，会形成两套目标理解、两套方案语义和两套错误恢复。

**建议**：Phase C 只做薄路由与绑定；原始目标原样交给现有项目咨询，方案、授权和执行继续复用现有真源。

### 2.2 最大产品风险：工作台替用户猜项目

主对话位于全局层，而执行事实属于项目。自动猜项目一旦猜错，后续方案、权限、记忆和审计都会落错归属。

**建议**：首版只认用户显式选中的当前项目与工作流。未选择、绑定不一致、多项目或跨项目要求，一律停止并提示用户选择，不做概率猜测。

### 2.3 最大安全风险：聊天入口绕过状态机

“说一句就启动”不等于“说一句就执行”。LM 不能直接推进事实状态，也不能把用户一句话当成执行授权。

**建议**：主对话最多创建待确认方案；唯一真实开工门仍是现有的「允许并开始」。秘书和全局主管都不能替用户点过这道门。

### 2.4 最大范围风险：把多轮澄清塞进第一刀

现有咨询方案没有正式的多轮澄清状态。首版若同时新增澄清会话、恢复协议、项目切换和执行接续，范围会从“薄接入”膨胀成新状态机。

**建议**：第一刀只做确定性前置检查：无项目、无工作流、空目标、跨项目或解析不确定时，返回人话提示并停住。真正的多轮澄清另做后续切片。

### 2.5 当前写权限回退不适合直接带进新入口

`h5_project_dispatch_bridge.rs` 当前在任务包缺少或给空 `allowed_write` 时，会退到整个 `project_root`。path-lock 仍限制在测试项目，但窄权限可能被放大为整个项目根。

**建议**：它不阻塞 Phase C 的“目标 → 待确认方案”部分，但在主对话真正接通「允许并开始 → 执行」前，必须单独改为 fail-closed 并做回归。该修改涉及安全边界，需要单独授权。

## 3. 候选方向比较

| 方向 | 收益 | 主要问题 | 建议 |
|---|---|---|---|
| 先全面清债 | 降低部分工程噪声 | 容易失去产品主线；多数债不阻塞用户价值 | 不选，只收执行前安全债 |
| 继续做整台原型或 UI 重画 | 能继续讨论形态 | 用户已明确不采纳；仍不能证明真链路 | 不选 |
| Phase C：主对话薄接入现有闭环 | 最接近“只说目标，Syn 组织工作”；复用最多 | 必须严格解决项目绑定和授权边界 | **推荐** |
| 提前做模型自适应、Phase D/E | 愿景能力更强 | 缺真实使用数据和前置能力；扩大风险 | 后置 |

## 4. 推荐目标：Phase C 不是“听懂一切”，而是“安全接入”

### 4.1 用户价值

用户不需要先找到项目交办页、理解咨询角色或学习固定命令。只要在主对话中、明确的当前项目上下文里说出目标，Syn 就能把目标送进现有方案与执行闭环。

### 4.2 首版行为契约

主对话收到输入后只能得到四类结果：

1. **可发起的新项目目标**：把用户原话和明确项目绑定交给现有项目咨询，生成待确认方案，然后停止。
2. **缺少确定性上下文**：例如没有当前项目、没有工作流或绑定冲突；提示用户先选择，零方案、零执行。
3. **意图不支持或含糊**：说明这一版还不能从主对话处理，并请用户补充或回到现有入口；不猜测、不误路由。
4. **纯咨询或纯建议**：允许形成只读咨询结果，但不能生成写授权或自动开工。

建议的行为流，不要求首版新增同名持久化状态：

```text
收到原话
  → 校验当前项目 / 工作流绑定
  → 判断是否为首版支持的“新项目目标”
      → 否：人话说明并停止
      → 是：调用现有项目咨询
          → 生成 PendingUserConfirmation 方案
          → 用户审方案
              → 拒绝 / 修改：不执行
              → 允许并开始：进入现有 B2 闭环
                  → 运行 / 求助 / 失败处置 / 终标 / 总结 / 交货
```

### 4.3 角色边界

- **主对话入口**：接收用户表达并呈现结果，不直接写业务事实。
- **秘书**：可以解释、提醒、转交；不直接派活、不确认事实、不写正式记忆。
- **项目咨询**：继续负责读项目、理解目标、生成方案。
- **控制核心**：校验项目绑定、状态、权限和执行门。
- **项目主管 / worker / 全局主管**：继续按现有 B2 职责工作，不因入口变化而改权。
- **用户**：继续掌握方案授权、方向变化和最终接受权。

## 5. 第一版范围

### 5.1 做

- 固定测试项目内，用户显式选择当前项目和工作流。
- 主对话接收一条新的项目目标。
- 保存原始输入，并把它原样交给现有项目咨询。
- 确定性检查空目标、缺项目、缺工作流、绑定不一致、跨项目和不支持意图。
- 生成现有类型的待确认方案，继续使用现有方案卡和授权门。
- 用户授权后复用 B2 全闭环。
- 为新入口记录项目绑定、原始目标、方案 ID、授权 ID 和最终运行关联，便于审计与回看。
- 保留原项目交办入口作为可用回退路径。

### 5.2 不做

- 不采纳或实现此前原型。
- 不重做整台工作台、不改左侧栏、不新增一套产品壳。
- 不自动猜项目、不自动切项目、不跨项目接力。
- 不新增第二套咨询 agent、方案 schema、任务包生产器或执行状态机。
- 不做开放式“什么都能聊、什么都能做”的通用助手。
- 不做正式多轮澄清协议。
- 不从主对话直接执行、自动批准或绕过现有授权卡。
- 不做自适应换会话 / 换模型。
- 不解锁非测试真实项目，不进入 Phase D/E。

## 6. 对现有能力的复用关系

| 环节 | 现有能力 | Phase C 真正新增的差量 |
|---|---|---|
| 自由文本目标 | 项目交办页已存在 | 主对话接收并保留原话 |
| 项目上下文 | 项目页天然已绑定 | 全局入口必须显式绑定并校验 |
| 目标理解与方案 | `run_project_consultation` + `ConsultationProposal` | 不新增第二套，只做安全转交 |
| 方案状态 | `PendingUserConfirmation` | 不变 |
| 方案授权 | 现有授权卡与人闸 | 不变 |
| 执行 | B2 任务包、会话、求助、终标、失败处置 | 不变 |
| 结果与记忆 | 交货、主管总结、候选记忆、审计 | 不变 |
| 新增核心 | 无 | 入口意图判定、项目绑定、停止反馈、关联审计 |

## 7. 推荐切片顺序

### Gate 0｜B2 真机盖章

先在固定测试项目完整走一单：出方案 → 允许并开始 → 逐步运行 → 造一次求助或失败 → 主管终标与四选一 → 总结、候选记忆和审计。

- 基础 E2E 先由开发线自验。
- 用户只做阶段末真实桌面最终验收。
- 若这一单不通过，停止 Phase C，只修 B2。

### C-NL0｜设计与差量冻结

- 明确 Phase C 的真实差量是“主对话路由 + 项目绑定”，不是新 NL 引擎。
- 只支持 `NEW_PROJECT_GOAL` 这一类可执行意图。
- 定义项目 / 工作流绑定输入、`UNKNOWN / STOP` 行为、审计关联和回退方式。
- 全仓查重并对照 `docs/2026-07-09-codebase-capability-map-v2.md`。
- 另行拍定主对话承载界面；不继承旧原型。

### C-NL1｜目标到待确认方案

- 固定测试项目、显式项目与工作流绑定。
- 主对话接收原话，通过确定性前置检查后调用现有 `run_project_consultation`。
- 生成现有 `PendingUserConfirmation` 方案后停止。
- 不新增第二个 LM 调用，不接真实执行。

### C-NL2｜接回现有授权与 B2

- 继续使用现有方案卡和「允许并开始」。
- 修复并验证 `allowed_write` fail-open 后，再接真实执行。
- 用户授权前必须保持零 worker、零执行、零写项目文件。
- 授权后复用 B2，不修改 B2 状态机、四选一、求助、终标和总结语义。

### C-NL3｜桌面验收与收口

- 在真实 Tauri 桌面窗口走通“主对话一句话 → 待确认方案 → 授权 → B2 交货”。
- 验证不支持意图、缺项目和绑定冲突都能诚实停住。
- 用户最终验收“我不用找入口和学命令，也能从一句话安全发起一单工作”。
- 验收通过后，才更新 `CURRENT.md`、路线图和现状说明书。

## 8. 必测场景

| 场景 | 期望结果 |
|---|---|
| 当前测试项目 + 明确目标 | 生成与项目页现有入口等价的待确认方案 |
| 未选择项目 | 提示选择；零方案、零执行 |
| 项目有多个工作流但未明确当前工作流 | 停止并请用户选择；不猜 |
| 输入同时涉及两个项目 | 明确首版不支持；不自动拆成两单 |
| 空输入或只说“继续弄一下” | 提示目标不足；不创建方案 |
| 纯咨询、无需改文件 | 只读方案；空写范围；不能出现“允许并开始改文件” |
| 用户拒绝或要求修改方案 | 零执行，保留可回退状态 |
| 用户批准方案 | 进入现有 B2，绑定链完整 |
| worker 求助或失败 | 继续走 B2 的 `waiting_decision` / 四选一，不被入口吞掉 |
| 重复提交同一输入 | 不重复创建运行链；结果可解释 |
| 项目 / 工作流绑定不一致 | 后端拒绝并给人话原因 |
| 入口关闭或 Phase C 失败 | 原项目交办路径仍可正常使用 |

## 9. 硬停止条件

出现以下任一情况，必须停止，不得用默认值继续：

- 当前项目不唯一或项目 / 工作流绑定不一致。
- 输入解析为未知、冲突或不支持意图。
- 请求跨项目、切项目或触及非测试真实项目。
- 方案范围、权限或验收字段缺失。
- `allowed_write` 缺失时退宽到项目根。
- 用户尚未授权。
- 新入口试图直接改事实状态或启动 worker。
- 产生重复方案、重复授权或重复运行链。
- 任何关键状态只存在聊天上下文，没有落入工作台事实层。

## 10. 回退策略

Phase C 必须是现有闭环前的一层薄适配：

- 新入口可单独关闭。
- 关闭后，项目页原有“说 → 出方案 → 批 → 跑”继续可用。
- 不迁移、不改写旧方案和旧运行记录。
- 不把 Phase C 的对话文本当成事实源；工作台 store、状态机、授权和审计仍是真源。

## 11. 拍板后才做的权威同步

本建议若获用户确认，再执行以下动作：

1. 新增 Phase C 开门决策，显式记录：仅固定测试项目内把“真 NL 主对话”从旧终局口径前移；非测试项目、多项目接力仍属于 Phase E。

5. 将本建议转成可执行任务包；在用户明确授权前，不修改安全闸。

## 12. 建议用户拍板的四件事

建议全部选择“是”：

1. **B2 真机验收通过后，下一阶段进入 Phase C。**
2. **Phase C 首版只支持显式选中的固定测试项目和一个新的项目目标。**
3. **主对话只生成待确认方案，不猜项目、不跨项目、不直接开工。**
4. **具体 UI 不沿用旧原型，在 C-NL0 行为契约拍定后另行设计。**
