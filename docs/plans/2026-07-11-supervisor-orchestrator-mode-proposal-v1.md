## 0. 一句话

**把编排权从状态机挪给主管 LM:主管作为一个真 codex 会话,通过工作台暴露的受控 MCP 工具自主派工、跟进、追问、收单——LM 编排,工具面治理,每个动作事前过闸全落账。**

## 0.1 站 3a 架构修订（2026-07-12）

本提案的 MCP 副作用工具面已被站 3a 控制核心桥替代并由 v7 真跑闭环：主管 LM 只输出一个结构化动作提议，Syn 重新绑定当前 run、授权、任务包、配额和账本修订后，才调用既有受控派发/续发/终标适配器。MCP 仅保留只读投影，不能再直接启动 worker、追问、终标或报告。此修订解决 Codex 外层工具审批在到达 Syn 前取消副作用的问题；经典管线与人闸不变。

职责正本是三层而非一份混合提示词：worker 只接收执行验收和回程契约；Syn 保存、检查、绑定、路由、推进状态和落账，但不静默改写任务含义；主管读取 Syn 转发的任务包、回程和证据后作判断，不能自造权限。新 proposal 原生保存三类验收，批准 UI 分栏显示，最终 worker prompt 只物化 worker 验收。v7 证明全新会话、唯一 worker、一次 inspect、advisory PASS 和用户报告均按此路径完成；证据见 `evidence/2026-07-12-orchestrator-station3a-control-core-bridge-v1.md`。

v7 后三轮独立复核又把账本身份边界收紧：binding 记录用完整身份 SHA-256，不再用可截断 slug；迁移同时修 binding 与 dispatch 引用，只有真实 legacy 候选可迁移，歧义旧引用整次拒写，保留历史 SHA 不会被改绑；授权快照和任务包指纹是真 SHA-256 且跨同一 run 动作贯穿；fresh 会话写真实创建 provenance；合法 worker 回程写回主管 worker 记录。现有 71 条 binding 已写前备份迁移为 71 个唯一 ID，352/352 条 dispatch 引用已同步且零孤儿。以上是 3a 风险清理，不扩展 3b 权限。

## 1. 诊断(为什么·实证齐全)

- 同一个 codex:kt-erp 里原生协作(父 agent spawn 团队·多轮跟进)又活又好;工作台里(exec 一次性寄信)又聋又笨——**差距不在任务包内容,在协作方式**:原生把 worker 当持续对话的伙伴(发起→跟进→追问→收→关全生命周期),我们只有「发起→收卷」两拍。
- codex 两种原生子级模式已勘实(threads.source 铁证):临时 subagent(用完即弃)/ thread_spawn 新开对话(持久·可续发消息·可指定模型·可 Worktree)。工作台现状=第三种:结构仿模式二但编排者是死代码。
- worker「没试就投降」「聋」「主管防御性瞎拆」全是死编排的病(07-10~11 实案六件)。

## 2. 方案(治理同步 = 工具面·非原生 spawn)

- **否掉原生 spawn 路**:父 agent 自生子时沙箱/写范围由它自定,工作台写闸插不进事前——与「治理同步」冲突;
- **工具面路(定)**:工作台暴露受控 MCP 工具给主管会话:
  `派工人(任务包)` `读口供` `追问工人` `等待` `读关键文件(拆前勘察)` `终标/收单` `报告用户`——每个工具物理上=现成工作台命令的包装(create_and_bind/dispatch/口供读模型/relay send/终标机),**allowed_write/绑定/口供/账本全部事前过闸**;
- **一轮 agent loop = 一单编排**:codex 单轮内本就是多步工具循环——主管一轮内完成派→等→读→追问→终标;长单用 resume 续(断点=工具幂等);
- **护栏**:工具侧配额(并发 worker 上限/追问预算/spawn 计数)·runaway 上限·人闸不动([允许并开始]仍是唯一开工门·主管编排发生在批准后的执行段)·全程账本(主管每次工具调用即审计事件)。
