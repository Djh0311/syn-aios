# 工作流画布架构 · 两面一引擎 · 方案 v1（2026-06-21）

> 状态：待开发（用户拍板：**两个画布 / 功能各自定义清楚 / 底层一个引擎、两种调用**）。
> 锚点：现有 `lib/canvasSurfaceBoundaries.ts`（已是两面边界种子）+ 蓝图 §11（项目内可编辑画布）+ `docs/plans/2026-06-21-workflow-session-and-scope-model-v1.md`（会话模型）。

## 0. 一句话
工作流画布 = **一套引擎、两种调用**。UI 上是两面（**实验画布 / 项目画布**），引擎只有一套**可编辑 React Flow 核心**，按 surface 配置渲染出不同能力与边界。现状是两套分叉实现（实验可编辑 / 项目只读）且**拧反**（蓝图要项目可编辑）；本方案收成「一引擎双调用」。两面的真正区别是**沙盒 vs 真实受控**（§4），不是功能多少。

## 1. 现状（核实物 2026-06-21）
- 两套独立实现：`views/CanvasView.tsx`（实验，**可编辑**：`nodesDraggable/Connectable`+建/连/编辑）、`views/projects/ProjectWorkflowCanvasView.tsx` 的 `ProjectWorkflowReactFlowCanvas`（项目，**只读**：`nodesDraggable={false}`，`RunningWorkflowsView` 也复用它）。节点类型两套（`nodeTypes` vs `projectCanvasNodeTypes`）。
- **但 `canvasSurfaceBoundaries.ts` 已有两面边界模型**：`experiment_canvas`（不写项目事实/正式记忆/工作流状态、非项目事实源、实验运行不写正式事实）、`project_workflow_canvas`（事实源=工作流状态派生读模型、运行经控制核心/权限/审计）。→ **功能定义的骨架已在，缺的是共用一个引擎。**
- **拧反**：蓝图 §11 要项目画布**可手动编排**（拖拽节点 / 步骤列表细调），现实项目画布只读；可编辑的反而是蓝图里没有的实验画布。（成因：项目画布走的是「画布优先重画 P1-P4 = 只读重画」，编辑能力先在实验画布原型了，没并回。）

## 2. 蓝图锚点
- §11：**一个**工作流画布，项目内（UI 蓝图路由 `/projects/:projectId/workflows/:workflowId`），**可手动编排**，**方案视图 ↔ 运行状态视图**切换（同一画布两视图），顶部**项目规则状态条**（§11.2），节点点开右侧详情（§11.3），**不用弹窗**。
- 实验画布是我们的增量（早期 / 试验 / 草图 / 模板库）；蓝图无此对象但不冲突——`experiment` 边界已声明「不是项目 workflow 事实源」。

## 3. 一引擎双调用（架构）
**共享引擎 `WorkflowCanvasEngine`**（从现 `CanvasView` 抽出）：React Flow 可编辑核心 —— 自定义 nodeTypes、拖/建/连、节点详情编辑面板（§11.3）、save/load、模板、会话策略（接会话模型方案）。引擎**不认死 surface**；能力开关 + 边界 + 运行目标 + 事实源全部由**调用配置注入**。

**调用配置 `CanvasSurfaceConfig`**（扩 `canvasSurfaceBoundaries`）：
```
{
  kind: "experiment" | "project",
  boundary: CanvasSurfaceBoundary,                 // 现成两面边界，直接复用
  projectRoot?: string,                            // project 才有
  capabilities: { edit, connect, createNode,
                  saveTemplate, manualOrchestrate },
  views: ("plan" | "run_state")[],                 // project 两视图；experiment 至少 plan
  realRunTarget: "fixed_test_project" | "bound_project",
  authority: "free_canvas_def" | "workflow_state_read_model",  // 事实源
  showProjectRuleBar: boolean,                     // project：§11.2 状态条
}
```
**两面 = 两个 config 调同一引擎。** 引擎读 config 决定渲染哪些能力 / 边界 / 视图。

## 4. 两面功能定义（划清——这是核心）

**核心轴 = 沙盒 vs 真实受控，不是功能多少。** 实验 = 沙盒（不碰真实项目、只模拟/测试、无真实后果 → 不需安全控制）；项目 = 项目内真实工作（**同样能自由编排**，但每个影响真实项目的动作受控制核心/权限/审计约束）。两面都能编排、都有成熟模式，区别在"真不真"。

| 维度 | 实验画布 experiment（沙盒） | 项目画布 project（真实·受控） |
|---|---|---|
| 作用域 | 不绑项目（模拟 / 测试 / 沙盒实验） | 绑定一个真实项目（蓝图 §11） |
| 编辑 | 自由编排全功能（建/拖/连/改） | **同样自由编排**，但真实动作受安全控制；蓝图「手动编排」，**现状只读、要补上** |
| 事实源 | 自由 `CanvasDefinition`（非项目事实源） | 工作流状态派生读模型（项目事实源） |
| 写什么 | 不写项目事实 / 正式记忆 / 工作流状态 | 经控制核心 / 权限 / 审计写项目工作流 |
| 视图/编辑入口 | 自由画布；+「清空画布」「新建画布」 | 默认显示当前工作流+运行状态；**无视图切换钮**；编辑=「编辑工作流」动作进草案→提交→通过；+「新建工作流」 |
| 规则状态条 | 无 | 有（§11.2：harness / 运行性 / 违规 / 证据） |
| 运行性检查 | 轻（实验语境） | 必做（可运行 / 有警告 / 不可运行，§11） |
| 真跑目标 | **固定测试项目**（现 C 双闸） | **该项目**（高危#1，控制核心 + 双闸，逐次授权） |
| 节点详情 | §11.3 那套（权限/模型/技能/验收/审查/harness） | 同（同一引擎） |
| 成熟模式 | 能做，但**草稿级**（没实战验证） | **真实成功运行沉淀的稳定模式（§26.4），稳定可复用——主来源**；可全局 or 项目私有（§22） |
| 会话策略 | new/resume 平级；new→测试项目建会话 | new/resume 平级；new→该项目建会话 |

> 成熟模式两面都有，但**质地不同**：实验 = 草稿/试验性，项目 = 实战验证、稳定可复用——「真实跑出来的才稳定」即此。

## 5. 会话模型怎么落（接前方案）
- 会话策略（new/resume **平级**）是**引擎级**能力，两面共用。
- 前方案的「作用域两档」**= 这里的两面**：scope 不再是画布内部开关，而是**你在哪个面**。实验面 `new`=在测试项目建会话；项目面 `new`=在该项目建会话。
- 模板跨面：实验面存的模板可在项目面实例化；实例化清 resume `thread_id`（**会话方案** §8.1）照旧。
- → `scope` 是**显式持久化字段**（`experiment`|`project`，**不靠 project_root 派生**）：默认按所在面置值、但独立存储，以支持"草案设计好、未绑项目"的中间态（§三.4 决策）。`session_policy` 不变。

## 7. 边界 / 护栏
- 抽引擎 / 配置 / UI = **轻档**（纯前端）。
- 真跑就在固定测试项目 = **轻档**（2026-06-22 下放；path-lock + 沙箱守住、去 env-CONFIRM 闸）；**非测试真实项目真跑 = 仍重档·高危#1·锁着**。

## 8. 决策（已拍板 2026-06-21；编辑流程经用户真机后改）
1. **项目面编辑流程 = 统一走草案**（取代原"空闲直改/在跑草案"的分情况）：项目页**默认显示当前（在跑的）工作流 + 运行状态**；点**「编辑工作流」**→ 切到编辑界面（改的是**草案、原工作流始终不动/继续跑**）→ **「提交」→ 通过**（运行性检查 / 控制核心·权限·审计；空闲轻、在跑重）→ 才落到工作流生效。**不分空闲/在跑，编辑一律走草案。** ✅ —（注：本条=项目编辑；会话方案 §8.1=模板清 thread_id，勿混。）
2. **项目页不做"方案/运行视图"切换钮**（编辑是**动作**、不是视图）；另设**「新建工作流」**入口。✅
3. **实验画布加「清空画布」「新建画布」管理按钮**（真机反馈：现在没有）。✅
4. **导航重构**：实验画布**扶正到显眼入口**；**删「运行中工作流」入口/概念**；**保留 `RunningWorkflowsView` 组件**（核实物：3 个离线测试的 fixture、非死码；只删 nav 入口）。✅（取代旧 §三.1。）

## 12. 多工作流（一个项目 N 个工作流）+ 提交语义（2026-06-22 拍板）
- **一个项目存 N 个工作流**（现状是一个项目一个 `default_workflow_id`；扩成 list/map，每个有 workflow_id / 名 / 状态 / nodes / edges）。
- 项目页 = 工作流**列表 / 选择器**：看有哪些、选一个查看/编辑、或**新建**。
- **新建工作流** = 造一个新 workflow_id（空白画布**本来就对**，不覆盖谁）→ 编辑 → 提交 → 经控制核心**新增**进该项目 workflow-state。
- **编辑工作流** = 选一个现有 → **把它的 nodes 加载进草案** → 改 → 提交 → 经运行性「通过」+ 控制核心**更新那一个**。
- 这把原「提交即替换 → 覆盖治理结构」的坑解了：**新建不碰旧的、编辑只动选中的那个、都过控制核心**。坑的根源就是"一个项目只有一个工作流"。
