# Syn 全局 Jarvis 综合能力与明确项目入口建议 v1

日期：2026-07-10

状态：**候选建议稿，未拍板，不是当前权威，不是任务授权，不改变 `CURRENT.md`、roadmap 或任何阶段安排。**

本文只讨论产品与架构关系，不采用此前前端原型，不定义下一阶段做什么，也不规定实现顺序。

---

## 0. 结论先行

> **全局的是能力，不是自然语言入口。统一的是感知、协调和治理，不是项目上下文。所有改变项目事实或执行项目工作的动作，都必须落到一个由用户明确进入的项目。**

本文建议把 Syn、项目、Jarvis、Agent、模型和工具的关系定义为：

```text
Syn       = 桌面工作台、共同制度和统一能力底座
项目      = 用户进入工作的明确位置，也是事实、权限和执行的归属
Jarvis    = 贯穿 Syn 全局的综合智能能力
Agent     = 被 Syn 组织和调度的具体职位角色
模型/工具 = 角色执行工作时使用的资源
```

因此，Jarvis 不应被做成一个让用户先交代所有事情、再由系统猜项目的全局聊天机器人。更准确的产品形态是：

> **一个 Syn，多个人可以明确进入的项目工作间；同一套 Jarvis 能力在全局感知整体，在项目内受控地帮助理解、组织、执行、监督和交货。**

---

## 1. 本文回答什么，不回答什么

### 1.1 本文回答

- Jarvis 作为 Syn 的全局综合能力究竟是什么。
- 全局能力如何在不制造“万能自然语言入口”的前提下服务所有项目。
- 用户如何始终清楚自己在哪个项目、哪个环境、正在做什么。
- 全局空间、项目入口、项目内工作和跨项目协调如何分工。
- 游戏、Agent、企业系统、个人工作和股票市场如何共用一套 Syn 底座。
- 全局能力如何受到项目、权限、记忆、凭据和审计边界约束。

### 1.2 本文不回答

- 下一阶段做什么。
- Phase C、Phase D 或其他阶段如何定义。
- 开发顺序、排期、任务拆包和里程碑。
- 具体页面最终布局和视觉稿。
- 是否采用此前任何原型。
- 是否开放真实企业生产、真实资金或无人值守执行。

上述事项如需决定，应另行讨论和拍板，不能从本文反推授权。

## 2. 已知事实、未知项与本文假设

### 2.1 已知事实

1. 当前架构已经把项目定义为最高级业务对象和主要隔离单元；控制核心掌握事实、权限、状态机、策略和审计。
2. Agent、模型、工具、知识、记忆存储、harness 和代码索引均通过适配器接入，适配器不能直接提权、推进状态或跨项目读写。
3. 秘书已经被定义为贯穿首页、项目、通知、待办、记忆和审计的核心协作角色，而不是固定在某个聊天页面里的功能。
4. 当前正式决策已经否定第二个主对话入口，保留项目内自由文本交办能力，并要求继续强化项目内入口。
5. 现有愿景坚持“Agent 管事，用户管决定”；确认、证据和审计是长期制度，不因模型变强而自动消失。
6. 当前 Provider 自带记忆仍存在跨会话注入的已知缺口，不能把不同项目的原始资料默认汇入同一个全局上下文。

### 2.2 仍未确定

- 一个“项目”的合理颗粒度：一个产品、一个业务目标，还是一个长期工作空间。
- 开发、测试、生产是否属于同一项目的不同环境，还是在高风险场景下拆成独立项目。
- 全局空间允许用户进行哪些治理操作，哪些只能跳转项目后处理。
- 跨项目协调单是否需要成为正式对象，以及它与各项目任务的关系。
- 股票市场未来是否只做研究与模拟，还是另行建设真实交易能力。

这些未知项不妨碍先把“全局能力、明确入口、项目执行”三者的边界说清楚。

### 2.3 本文采用的安全假设

- 全局空间可以读取受控的项目摘要，但不默认读取项目原始上下文。
- 用户通过明确点击、选择或打开动作进入项目，系统不能仅凭语言内容自动切换项目。
- 自然语言可以存在于项目内，但它只是项目内的一种交互方式，不是 Syn 的全局工作入口。
- 未明确项目时，全局层可以解释、汇总和建议，但不能执行项目写操作。
- 企业生产、外部发送、个人账号操作和真实资金动作始终需要更窄的环境与权限边界。

## 3. Jarvis 的准确产品定义

### 3.1 Jarvis 是什么

Jarvis 是 Syn 统一提供的一组综合能力：

- **全局态势感知**：知道有哪些项目、各自处于什么状态、哪里异常、哪里需要用户决定。
- **目标理解**：在用户已经进入明确项目后，理解目标、约束和上下文缺口。
- **组织协调**：为项目选择合适的职位、模型、工具、知识和工作流。
- **运行监督**：发现任务停滞、上下文污染、工具故障、权限不足和验收失败。
- **会话与模型治理**：判断是否需要重锚、换会话或换模型，并按角色影响面决定自动处理还是提醒用户。
- **记忆治理**：区分临时上下文、项目事实、项目经验、领域知识和全局偏好。
- **权限与风险治理**：在执行前说明范围，在执行中阻止越界，在执行后留下证据和审计。
- **交货与解释**：把结果、证据、失败和下一步用人能理解的方式呈现。
- **跨项目发现**：发现项目间依赖、冲突、复用机会和资源竞争，并形成可见建议。

这些能力可以出现在全局总览、项目首页、项目交办、运行过程、通知、待办、记忆和审计等多个位置。Jarvis 的“全局”指能力贯穿整个 Syn，不指必须有一个统一聊天框。

### 3.2 Jarvis 不是什么

Jarvis 不等于：

- 一个全局自然语言输入框。
- 一个拥有全部项目上下文的超级会话。
- 一个可以直接操作所有项目的万能 Agent。
- 一个名为 `JarvisService` 的新架构中心或拥有独立权力的新角色。
- 一个自动猜测用户想进入哪个项目的路由机器人。
- 一个拟人头像、悬浮球或独立页面。
- 一个绕过项目主管、权限、状态机和用户确认的新权力中心。

### 3.3 “全局能力，项目内生效”

同一套 Jarvis 能力在不同位置具有不同权限：

| 位置 | Jarvis 可以做 | Jarvis 不可以做 |
|---|---|---|
| 全局空间 | 汇总项目摘要、发现异常、聚合待决策、提出协调建议、解释系统状态 | 猜项目、继承任一项目原始上下文、直接修改项目、使用项目凭据 |
| 明确项目内 | 理解目标、组织角色、生成方案、监督执行、治理会话与模型、汇总证据 | 越过当前项目范围、静默扩大权限、替用户批准关键决定 |
| 跨项目协调 | 列出受影响项目、说明依赖、形成协调建议和信息流转清单 | 创建混合上下文后一次性跨项目执行 |

一句话：

> **Jarvis 可以在全局看见结构，在项目内参与工作，但不能把“看得见”自动升级成“有权做”。**

### 3.4 Jarvis 不替代现有角色和制度

Jarvis 是现有能力共同形成的产品体验，不应把原有职责揉成一个超级对象：

- **秘书**负责汇总、提醒和解释，不因“Jarvis 全局能力”而获得派活、审批或项目写权限。
- **全局主管**继续提供复核意见，不因 Jarvis 存在而变成自动审批闸。
- **控制核心**继续掌握事实、权限、状态机、确认和审计。
- **项目咨询、项目主管和 worker**继续在明确项目内分别承担理解、组织、执行和验收职责。
- **记忆层和适配器**继续遵守各自边界，不能通过 Jarvis 名义跨项目或绕过核心。

因此，“Jarvis 是 Syn 的全局综合能力”是产品能力定义，不是授权新增一个更高权限的运行实体。

## 4. 建议的产品结构

```text
Syn 桌面工作台
├── 全局空间
│   ├── 今日关注
│   ├── 运行与异常
│   ├── 待我决定
│   ├── 最近交货
│   ├── 跨项目依赖
│   └── 全局制度与资源状态
│
├── 游戏项目组
│   └── 具体游戏项目
├── Agent 项目组
│   └── 具体 Agent 项目
├── 企业系统项目组
│   └── 具体企业项目
├── 个人项目组
│   └── 具体个人项目
└── 市场项目组
    └── 具体研究、模拟或未来独立交易项目
```

“游戏、Agent、企业、个人、市场”适合作为项目分类、项目模板或内部领域配置，不应取代具体项目成为模糊的执行范围。

全局空间是一个明确的位置，但它是总览与治理位置，不是“什么都可以从这里说一句然后直接开工”的入口。

## 5. 明确项目入口

### 5.1 左侧栏是主导航，不是装饰

建议永久保留左侧项目入口。用户不应依赖模型判断自己在哪里，也不应先打开聊天再询问当前上下文。

每个项目入口至少应让用户知道：

- 项目名称与稳定图标。
- 项目类型。
- 当前状态：空闲、运行中、等用户决定、失败或已交货。
- 当前环境：开发、测试、生产、研究、模拟或实盘。
- 是否存在需要用户处理的事项。

项目分组可以帮助查找，但分组不能隐藏当前项目身份，也不能成为新的执行归属。

### 5.2 当前项目身份必须持续可见

进入项目后，任意页面都应持续展示：

```text
当前位置：项目名称
当前环境：开发 / 测试 / 生产 / 研究 / 模拟 / 实盘
当前目标：正在推进的目标
当前状态：运行中 / 等待决定 / 失败 / 已完成
当前工作：正在做的任务或步骤
当前责任：哪个职位正在处理，是否需要用户介入
```

这条身份信息不能因为用户打开聊天、文档、知识库、画布、运行详情或审计而消失。

### 5.3 项目切换必须是真切换

项目切换不仅是换一个页面标题，还必须重新绑定：

- 项目事实和当前快照。
- 临时对话上下文。
- 可召回记忆范围。
- 知识与文件根。
- 角色、模型和工具策略。
- 凭据、账号和网络范围。
- 权限快照和审计归属。

如果上一个项目存在未提交输入、待确认方案或正在进行的操作，切换前应明确提示。系统不能把上一个项目的临时上下文悄悄带入下一个项目。

### 5.4 自然语言只在明确范围内解释

用户进入项目后，可以用自然语言表达目标，因为项目范围已经通过界面和系统确定。

此时自然语言只负责表达：

- 想完成什么。
- 有哪些偏好和限制。
- 哪些地方需要分析或创造性判断。

自然语言不负责决定：

- 当前属于哪个项目。
- 可以读取和写入哪里。
- 可以调用哪个账号或凭据。
- 是否进入生产或实盘。
- 是否已经获得执行授权。

## 6. 全局空间的建议边界

### 6.1 全局空间允许

- 查看所有项目的受控摘要。
- 查看运行、异常、待决策、近期交货和风险变化。
- 查看角色、模型、工具、知识源和系统连接是否健康。
- 查看跨项目依赖和冲突建议。
- 管理全局稳定偏好、制度和资源注册信息。
- 点击事项后进入对应项目处理。
- 在明确列出参与项目后，形成跨项目协调建议。

### 6.2 全局空间不允许

- 提供一个默认拥有所有项目权限的万能输入框。
- 根据一句话自动猜测或切换项目。
- 默认加载全部项目对话、文件、记忆和工具输出。
- 在未进入项目时直接创建项目事实或推进工作流。
- 因为能看到项目摘要就取得项目写权限。
- 直接使用企业、个人或市场账户凭据。
- 把多个项目拼成一个没有清晰归属的长期会话。

### 6.3 全局提醒如何处理

全局提醒应回答：

- 哪个项目发生了什么。
- 为什么值得关注。
- 当前是否只是信息，还是需要用户决定。
- 点击后将进入哪里。

真正的查看详情、确认、修改或执行，应在对应项目内完成。

## 7. 项目内 Jarvis：同一能力的受控投影

项目内 Jarvis 不是另一套 Jarvis。它是 Syn 全局能力在当前项目范围内的具体表现。

项目内可以具备：

1. **理解**：读取本项目允许范围内的事实、资料和记忆，理解用户目标。
2. **规划**：形成方案、任务、验收标准和允许范围建议。
3. **组织**：选择合适职位、模型、工具和知识源。
4. **执行**：在用户批准和控制核心约束下进入现有执行闭环。
5. **监督**：识别停滞、失败、求助、上下文异常和模型能力不足。
6. **恢复**：按治理规则重锚、换会话、换模型或请求用户决定。
7. **交货**：汇总做成了什么、证据是什么、风险和剩余问题是什么。
8. **学习**：提出记忆候选，但不自动把聊天或工具输出升级成正式记忆。

用户不需要理解内部有多少 Agent、模型或路由对象。界面首先表达的是：

- 我在哪里。
- 我正在做什么。
- Syn 接下来会做什么。
- 为什么停住。
- 需要我决定什么。
- 最终交付了什么，凭什么相信。

## 8. 跨项目协调

有些真实工作会同时影响多个项目。此时不建议让 Jarvis 在后台静默串联，而应形成显式的“跨项目协调建议”。

协调建议至少说明：

- 为什么需要跨项目。
- 涉及哪些项目。
- 每个项目分别提供什么、接收什么、执行什么。
- 哪些信息允许跨项目流转。
- 是否含敏感资料或凭据。
- 各项目将分别形成哪些任务、确认和审计。
- 哪些事项只是建议，哪些已获用户许可。

建议的关系是：

```text
全局 Jarvis 发现依赖
  → 形成跨项目协调建议
  → 用户明确选择参与项目和允许流转的信息
  → 各项目分别收到自己的工作
  → 各项目独立确认、执行、交货和审计
  → 全局只汇总结果
```

跨项目协调对象只描述关系，不取代项目成为新的事实和执行根。

## 9. 全局能力与项目能力的分工

| 能力 | 全局空间 | 项目空间 |
|---|---|---|
| 状态感知 | 聚合项目摘要和异常 | 展示项目详细事实和运行状态 |
| 主动提醒 | 告诉用户哪个项目值得关注 | 解释该项目为什么需要处理 |
| 目标理解 | 不猜项目、不建立项目执行上下文 | 在当前明确项目内理解目标 |
| 规划与执行 | 不直接执行项目工作 | 形成方案，确认后受控执行 |
| 跨项目协调 | 发现依赖并形成可见建议 | 接收本项目对应的工作 |
| 模型与会话治理 | 汇总质量、成本和异常趋势 | 按当前角色和项目政策处置或提醒 |
| 记忆治理 | 管理稳定偏好、制度和迁移候选 | 管理项目事实、经验和任务上下文 |
| 权限与凭据 | 管理注册、策略和健康摘要 | 使用当前项目授权的窄范围能力 |
| 审计 | 聚合索引和风险摘要 | 保存项目完整事件和证据 |

## 10. 五类业务如何进入 Syn

五类业务共用 Syn 的项目、权限、角色、执行、记忆和审计制度，但在项目配置上保留差异。

| 项目类型 | Jarvis 在项目内重点能力 | 必须持续可见的特殊边界 |
|---|---|---|
| 游戏开发 | 设计、代码、美术任务、构建、测试和可玩证据 | 版本、分支、构建目标、发布环境 |
| Agent 开发 | Prompt、Skill、工具、评测、模型与行为对比 | 角色版本、模型绑定、评测集、权限变化 |
| 企业系统 | 需求、开发、测试、数据变更说明和回滚 | 租户、数据级别、开发/测试/生产、外部写入 |
| 个人工作 | 计划、知识、文件、提醒和个人事务协助 | 隐私范围、账号、外发对象、设备权限 |
| 股票市场 | 数据核验、研究、回测、观察和模拟复盘 | 数据来源与时间、市场、币种、研究/模拟/实盘 |

这些类型适合作为项目背后的领域配置概念，用来决定默认工具、知识、模型、风险和验收规则。`DomainProfile` 只能作为便于讨论的候选名称，本文不拍板新 schema、插件系统或实现对象。它们不应成为用户必须先理解的复杂架构，也不应形成五套独立状态机。

市场研究、企业生产和个人外部账号尤其不能因为 Jarvis 是全局能力，就共享凭据或自动获得写权限。

## 11. 记忆、知识、凭据和数据边界

### 11.1 建议的记忆层次

```text
全局制度与稳定用户偏好
  → 经确认的领域通用知识
    → 项目事实与项目经验
      → 当前任务和会话临时上下文
```

原则：

- 全局 Jarvis 可以知道项目摘要，但不默认拥有全部项目原始资料。
- 项目事实不得因“以后可能有用”自动升为全局记忆。
- 项目内容向领域或全局提升时，应形成有来源、适用范围、敏感级别和有效期的候选。
- 跨项目信息流转必须可见、可追溯、可撤回或废弃。
- 聊天、搜索结果、模型摘要和工具全文不能直接成为正式事实。

### 11.2 凭据边界

- 凭据按项目、账号、环境和工具绑定。
- Agent 和普通模型上下文不应获得原始密钥。
- 全局层可以知道“连接是否可用”，不应因此获得“使用该连接”的权限。
- 企业生产、个人账号和未来实盘账户不与研究、开发或通用 Jarvis 上下文共用凭据。
- 项目切换必须重新计算和绑定可用能力，不能沿用上一个项目的凭据句柄。

### 11.3 环境边界

每个项目动作除 `project_id` 外，还必须明确环境：

- 软件：开发 / 测试 / 预发布 / 生产。
- 市场：研究 / 模拟 / 实盘。
- 个人事务：草稿 / 待确认外发 / 已外发。

“在哪个项目”解决业务归属，“在哪个环境”解决动作后果。两者都不能只靠颜色暗示，必须有文字和结构化状态。

## 12. 典型使用例子

### 12.1 继续一个游戏项目

用户从左侧栏进入 `Crazytown`。

项目持续显示：

```text
当前位置：游戏 / Crazytown
环境：开发
当前目标：完成运行验证
状态：等待你的决定
```

用户说“继续处理 NPC 对话证据问题”。Jarvis 只使用 Crazytown 被允许的上下文形成方案，不再猜项目，也不能读取企业项目的资料。

### 12.2 查看全局态势

用户进入全局空间，看到：

- Crazytown：一项验证异常。
- Syn：两项工作运行中。
- 企业 ERP：一项生产权限申请。
- 市场研究：一个数据源已经过期。

全局 Jarvis 可以解释、聚合、排序和提醒。用户点击 ERP 权限申请后进入 ERP 项目，再查看详情或决定；全局空间不直接批准。

### 12.3 发现跨项目依赖

Jarvis 发现某个 Agent 工具升级可能同时影响 Syn、游戏和企业项目。

它生成：

```text
影响项目：Syn、Crazytown、ERP
发现依据：共同使用工具 X
建议动作：分别执行兼容性检查
目前不会做：修改任何项目
```

用户明确选择参与项目后，各项目分别接收自己的工作和证据，不建立一个混合了全部原始上下文的超级会话。

### 12.4 项目内换会话或换模型

在明确项目内，普通执行角色的上下文已经污染。Jarvis 可以按照该项目的治理策略生成交接并处理。

如果被更换的是关键判断角色，项目内明确提醒：

```text
建议更换模型
原因：当前模型连续无法完成关键判断
影响：判断角度和行为风格可能变化
当前动作：等待你的确认
```

全局能力负责持续监测和统一制度，具体动作仍归属当前项目、当前角色和当前权限。

### 12.5 市场研究

用户明确进入“美股研究 / 半导体观察”项目。

项目持续显示：

```text
类型：市场研究
模式：只读研究
数据时间：2026-07-10 14:30
实盘权限：无
```

Jarvis 可以分析、比较和提醒，但不能因为它是 Syn 全局能力就获得券商账户或真实下单权限。

## 13. 设计验收原则

以下是产品设计是否成立的判断标准，不是当前阶段的开发验收或实施承诺。

### 13.1 位置清晰

任意页面、弹层或截图下，用户三秒内能够回答：

- 我现在是在全局空间还是具体项目。
- 如果是项目，是哪个项目。
- 当前处于什么环境。

### 13.2 工作清晰

用户能够立即看到：

- 当前目标。
- 当前状态。
- 正在做什么。
- 谁在处理。
- 为什么停住。
- 下一步会发生什么。

### 13.3 范围不可猜测

没有明确项目或明确全局治理范围时，不得执行项目写操作。语言内容不能静默改变当前项目。

### 13.4 全局能力不依赖全局聊天

即使完全没有全局聊天框，Jarvis 的全局感知、提醒、协调、会话与模型治理、权限、记忆和审计能力仍然成立。

### 13.5 项目切换真实发生

切换项目必须同时改变上下文、工具、凭据、权限、记忆和审计归属，而不只是改变页面标题。

### 13.6 跨项目流转可见

任意跨项目信息或任务都能回答：

- 从哪里来。
- 到哪里去。
- 为什么需要。
- 允许传递什么。
- 谁确认过。

### 13.7 主动但不越界

Jarvis 可以主动发现、解释、提醒和建议；是否执行由项目、环境、权限和风险规则决定。

### 13.8 新手不需要理解内部术语

界面首先表达“在哪里、做什么、会发生什么”。Agent、模型、路由、适配器和内部状态机属于按需展开的信息。

### 13.9 关键判断有人负责

普通执行恢复可以按制度自动处理；关键角色、生产环境、外部发送和资金动作必须明确提醒用户。

### 13.10 没有模型时仍然清晰

即使模型暂时不可用，项目导航、当前状态、权限、审计、已有结果和待用户决定事项仍然可见、可理解。

## 14. 明确反对的设计

- 用全局万能聊天框代替项目导航。
- 让 Jarvis 自动猜项目或静默切换项目。
- 所有项目共用一个长期自然语言上下文。
- 建立默认汇入全部原始资料的全局记忆池。
- 全局发现异常后直接跨项目执行。
- 让项目切换只改变 UI，不改变上下文和权限。
- 让五类业务各自复制一套角色、状态机、记忆和审计。
- 用拟人形象代替范围、状态、风险、证据和责任表达。
- 让用户必须理解 Agent、模型和路由术语才能完成普通工作。
- 因为 Jarvis 是全局能力，就让它持有所有项目原始凭据。

## 16. 一句话总结

> **Syn 不通过一个万能入口让用户“相信它知道自己在哪里”，而是通过明确项目入口让用户“看见它在哪里”；Jarvis 则在这套明确结构之上，提供贯穿全局的感知、协调、治理与智能执行能力。**
